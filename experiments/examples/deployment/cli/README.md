# qhufdel_cli

`qhufdel_cli` runs on Windows and applies a Q-HUFDEL update package to a
current model. It then compares the restored model with the expected next
model. The CLI uses the same decoder library and decode flow as the STM32F411
and ESP32-S3 firmware benchmarks.

## Getting Started

The command requires three input files:

- A current model.
- The expected next model.
- A Q-HUFDEL update package.

From this directory, the basic workflow is:

```powershell
cmake -S . -B build -G Ninja
cmake --build build
bin\qhufdel_cli.exe --current current.tflite --next next.tflite --package update.bin
```

The executable is copied to `bin\qhufdel_cli.exe` after a successful build.
The binary is statically linked on MinGW, so it does not require MinGW runtime
DLLs beside the executable.

## Build

### Requirements

- Windows
- CMake 3.16 or newer
- A C11 compiler, such as MinGW-w64 GCC
- Ninja, or another CMake generator such as `MinGW Makefiles`

For MSYS2 UCRT64, install GCC with:

```sh
pacman -S mingw-w64-ucrt-x86_64-gcc
```

Build with Ninja:

```powershell
cmake -S . -B build -G Ninja
cmake --build build --target qhufdel_cli
```

Alternatively, use MinGW Makefiles:

```powershell
cmake -S . -B build -G "MinGW Makefiles"
cmake --build build --target qhufdel_cli
```

The CLI reuses these libraries from the repository root:

```text
decoder/
third-party/crc32/
```

## Run

```text
qhufdel_cli -c <current> -n <next> -p <package.bin> [options]
```

Example:

```powershell
bin\qhufdel_cli.exe `
    --current LeNet-5_1-quantized.h `
    --next LeNet-5_3-quantized.h `
    --package Q-HUFDEL_LeNet-5_1_3.bin `
    --iterations 20 `
    --out restored.h
```

Use `--help` to print the same usage information in the terminal. Use
`--version` to print the CLI version.

## Options

### Required options

| Option | Description |
|---|---|
| `-c, --current <file>` | Current model. Accepts a C header such as `.h`, or a raw model file such as `.tflite` or `.bin`. |
| `-n, --next <file>` | Expected model after the update. Accepts a C header or a raw model file. |
| `-p, --package <file>` | Q-HUFDEL update package, usually a `.bin` file. |

### Execution and timing options

| Option | Default | Description |
|---|---:|---|
| `-i, --iterations <N>` | `1` | Decode the package `N` times for timing. Valid range: `1` to `1,000,000`. |
| `--chunk-in <B>` | `512` | Number of package bytes read per input chunk. Valid range: `8` to `16,777,216`. |
| `--chunk-out <N>` | `256` | Number of decoded values produced per output chunk. Valid range: `1` to `16,777,216`. |
| `-m, --in-memory` | off | Load the complete package into memory before decoding. This removes package file I/O from the run. |
| `-v, --verbose` | off | Print results for every iteration. Without this option, only the first iteration is logged. |

### Output and information options

| Option | Description |
|---|---|
| `-o, --out <file>` | Write the restored model after the timed iterations. A `.h` extension writes a C header; any other extension writes raw binary. This extra pass is not timed. A failed package does not produce an output file. |
| `-h, --help` | Print usage and option information, then exit. |
| `--version` | Print the CLI version, then exit. |

## Model Files

The loader accepts raw model files and C-style array headers generated by
`xxd -i` or the model export scripts. A header can contain an array in this
form:

```c
const unsigned char model[] = { 0x20, 0x00, 0x01, 0x02 };
```

The array name can be arbitrary. An optional `<name>_len = N;` declaration is checked against the number of bytes parsed. Header comments and include guards are ignored.

## Exit Codes

| Code | Meaning |
|---:|---|
| `0` | The restored model matches the expected model and the package CRC is valid. |
| `1` | The package decoded, but the restored model differs from the expected model. |
| `2` | Package error: invalid magic, header, codebook, payload, or CRC. |
| `3` | Input or usage error: missing file, invalid model header, or incompatible model pair. |

## Decode Flow

The host CLI preserves the firmware decode flow:

1. Read the package and update the running CRC-32.
2. Verify the package magic code.
3. Decode the 40-byte package header.
4. Rebuild the canonical Huffman codebook.
5. Decode the payload in chunks.
6. Apply the decoded delta to the current model.
7. Compare the restored model with the expected model.
8. Verify the package CRC.

File access uses `fopen` and `fread` instead of FatFs. Timing uses Windows `QueryPerformanceCounter`. Package I/O and model comparison are measured separately from decode time, and throughput is calculated from package size and average decode time.
